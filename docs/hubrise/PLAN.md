# HubRise integration: implementation plan (tsb-service)

Status: implemented in `tsb-service` on branch `feat/hubrise` (T1 to T9, see the "As built" notes at the end). The operator runbook is [README.md](README.md). The dashboard page and the other client work (section 15) are follow-ups outside this repository.
Scope of this workflow: `tsb-service` only. Client work (tsb-dashboard, tsb-core, tsb-mobile, tsb-pos-android, tsb-infra) is listed in section 15.

## 1. Goals and the one rule that governs everything

Features (all optional, all toggleable):

1. Push webshop orders (web and app) to HubRise.
2. Keep the menu and the HubRise catalog in step, in ONE of two directions chosen by the owner (never both): IMPORT (a HubRise catalog is the menu source of truth: products, SKUs, option lists, prices, categories, SKU codes) or PUBLISH (the dashboard is the single owner of the menu and every edit is published to the HubRise catalog, which the EPOS reads; amendment A15, owner decision of 2026-10-24: "only the dashboard edits the menu").
3. Order status changes made in HubRise flow back into tsb-service orders and the existing customer notifications and PubSub subscriptions.
4. HubRise inventory (sold out) drives product availability, and a manual sold-out toggle in the dashboard flows back to HubRise.
5. STANDALONE MODE: a restaurant that does not use HubRise behaves exactly as today.

The rule: **HubRise is an additive layer, never in the critical path.** Placing an order, paying, serving the menu and the dashboard must work identically when HubRise is unconfigured, disabled, unreachable or returning errors. The webshop reads only local tables; HubRise data is copied in by background jobs, and local events are pushed out through a durable outbox.

## 2. What the exploration found (facts the design depends on)

Backend facts (tsb-service at 554ccfa):

- **Catalog model.** `products` (price numeric(10,2), `code`, `slug` NOT NULL-ish unique, flags, `vat_category`, `is_visible`, `is_available`), `product_categories` (`order`, unique NOT NULL `slug`), translation tables with `language` CHECK in (en, fr, nl, zh). Choices are **per product**: `product_choice_groups.product_id`, `product_choices.product_id + choice_group_id`, with `min_selections >= 0`, `max_selections >= 1`, `min <= max`, `price_modifier >= 0` (CHECK). Orders reference them through `order_product_choices` (re-verified in `20260428130000_choice_groups_and_multi_selections.sql`: `product_choice_group_id` and `product_choice_id` are plain FKs without cascade, so the database refuses to delete a choice or group used by an order; the `ON DELETE CASCADE` seen on `20260220205101` belongs to the translation table and to `product_choices.choice_group_id`). The importer still never calls `DeleteChoice` / `DeleteChoiceGroup` / `DeleteProduct`: it only flips `is_available` / `is_visible`.
- **Order history is fragile.** `order_product.product_id` is `ON DELETE CASCADE`. Deleting a product destroys order lines. The integration must NEVER delete products: it retires them (hidden and unavailable).
- **`order_product` does not snapshot** product name, code or base price. `unit_price` is an average per unit that includes option surcharges. HubRise needs the base SKU price and the options separately, so the item part of the push payload is snapshotted into the outbox row when the order becomes actionable (the status and the SKU refs are resolved at send time, section 6.1).
- **Selection quantities** in `order_product_choices.quantity` are totals for the whole line (group min/max are multiplied by the line quantity, see `domain.PriceLine`). HubRise option quantity is per single item unit. Lines whose selections are not divisible by the quantity must be split per unit (section 7).
- **Order actionable moments.** Cash orders: end of `CreateOrder` resolver (where `SendNewOrderPush` is called). Online orders: the `default` case of the Mollie webhook paid branch (`payment/interfaces/handler.go`, after the cancelled/failed/test exclusions, next to `notifier.SendNewOrderPush`). These are exactly the moments to enqueue the HubRise push. Online orders must not be pushed before payment (HubRise integration guide says the same). Mollie redelivers webhooks, so the enqueue must be idempotent (section 6.1).
- **Single chokepoint for order status writes (verified).** `orders.order_status` is written only by `OrderRepository.Update` (called solely from `orderService.UpdateOrder`, `order/application/service.go`) and by `CancelStaleTestOrders` (store-review test orders, which are never pushed). `orderService.UpdateOrder` is reached from the GraphQL `UpdateOrder` mutation (through `order_settlement.go`), from `paymentService.HandlePaymentFailed` (Mollie cancelled/failed/expired) and from the POS paths that use the same service. The outbound status hook therefore lives in `orderService.UpdateOrder` (an optional observer port), NOT in the resolver.
- **The status-change orchestration lives inside the GraphQL resolver** `mutationResolver.UpdateOrder` (about 400 lines): payment settlement and Mollie refund on cancel (`cancelOrder`, advisory lock), no reopening of refunded orders, confirmation / ready / cancelled / refund emails, APNs + FCM alerts, Live Activity and Android live update, "late notification" suppression, `orderUpdated` PubSub topics. A HubRise status callback must reuse all of it, so it has to be extracted into a reusable method (task T3). This is the riskiest refactor in the plan; the existing test suite is the safety net.
- **Dual DB pool.** `DBPool.ForContext(ctx)` returns the Admin pool for staff contexts (`utils.SetIsAdmin`). Background jobs and webhooks must run with an admin context, or the HubRise repositories take `pool.Admin` directly (as `audit.NewRecorder(dbPool.Admin)` does). New tables get no per-role GRANTs in this repo (no migration contains GRANT), so the Admin pool is the only one that touches them.
- **Production runs 2 replicas** (k3s, `replicas: 2`). Every worker must be safe to run twice and no correctness rule may depend on process memory: `FOR UPDATE SKIP LOCKED` claims for queues, a DB lease row (`hubrise_job_leases`, compare-and-set) for singleton jobs, `pg_advisory_xact_lock` (transaction scoped, safe with pooled connections) for the catalog import, DB-backed debounce. Session-level advisory locks are not used for HubRise jobs.
- **Client IP behind Cloudflare (verified).** `router.TrustedPlatform = gin.PlatformCloudflare` in `main.go`, so `c.ClientIP()` is the CF-Connecting-IP and the existing per-IP limiters key on the real client, not on the tunnel address.
- **Go 1.27 pitfall** (memory note): a nil `json.RawMessage` is written as SQL NULL and cannot be scanned back. All new jsonb columns are `NOT NULL DEFAULT '{}'` and written from non-nil values.
- **Tests** use a shared PostgreSQL container per package (`internal/api/graphql/testhelpers`, dockertest, goose migrations applied once into a template database). CI gate: 98 % statement coverage (`scripts/coverage-check.sh`, excludes generated code, testhelpers, fakeupstream, cmd/). Local runs use `CGO_ENABLED=0`.
- `product/domain/vat.go` only mentions HubRise in a comment on `ServiceType` (mirror of HubRise service types). No other existing code to reuse.
- `restaurant_config` is a single-row table (`id BOOLEAN PRIMARY KEY CHECK (id)`): one installation = one deployment = one database. White-label brands (tokyosushi, ygfliege) are separate deployments, so "per installation" equals "single row".

HubRise facts (read from the official docs at www.hubrise.com/developers, and from `moyun-pos/crates/pos-hubrise*`):

- Base URL `https://api.hubrise.com/v1`, header `X-Access-Token`. OAuth at `https://manager.hubrise.com/oauth2/v1` (`/authorize`, `/token` with HTTP Basic client auth and a form body `code=`, `/revoke`). Authorization codes are one-use and expire after 10 minutes. **Access tokens do not expire** and have no refresh; a 401 means revoked, blocked or unpaid, and the connection must be flagged and the user told to reconnect.
- Scopes: `location[orders.write,catalog.read,inventory.read,inventory.write]`. (`catalog.*` also grants inventory, deprecated, so request `inventory.*` explicitly.)
- Active callbacks: HubRise POSTs the event JSON to our URL with header `X-HubRise-Hmac-SHA256` = hex HMAC-SHA256 of the **raw body** keyed with the **client secret**. We must answer 200 to 499 within 20 s; otherwise HubRise retries up to 6 times with 1 min doubling to 32 min, then deletes the event. Unacknowledged events stay readable at `GET /callback/events`. A client **never receives events it generated itself**. One callback per connection (`POST /callback` replaces).
- Event envelope: `id, resource_type, event_type, created_at, <resource ids>, previous_state, new_state`. Order create/update events carry `new_state`. **Catalog events carry no state** (re-fetch). Inventory events carry state only for `patch` (`state_change`).
- Orders: `POST /location/orders` (almost everything optional). Statuses: `new, received, accepted, in_preparation, awaiting_collection, in_delivery, completed` plus `rejected, cancelled, delivery_failed`; `awaiting_shipment` is a deprecated alias of `awaiting_collection`. `private_ref` is visible only to the client that set it (usable as an idempotency key: `GET /location/orders?private_ref=`). Payments omitted means unpaid. Prices are `"8.90 EUR"`, quantities decimal strings. HubRise does not compute tax.
- Catalog: `GET /catalogs/:id` returns everything (variants, categories tree, products with `skus`, `option_lists` with `options`, deals, discounts, charges). `GET /catalogs/:id` and order list reads are limited to **10 requests per minute** on top of 500/min, 2,500/h, 10,000/day. SKU `ref` is what orders carry (EPOS ignore or reject items without refs). Option lists: `min_selections` (default 0), `max_selections` (null = unlimited), `multiple_selection`. Restrictions: `enabled`, `variant_refs`, `dow`, time and date windows. `price_overrides` by variant and conditions (last matching rule wins). Product `tax_rate` per service type (`delivery`, `collection`, `eat_in`). `custom_fields` on SKUs, `tags` on categories, products, SKUs, options.
- Inventory: `GET/PUT/PATCH /location/inventory` (unscoped, recommended), entries `{sku_ref|option_ref, stock, expires_at}`; `stock "0"` is sold out, `expires_at` only with stock 0, `PATCH` with `stock: null` removes the entry (unlimited). Expiry of an entry triggers an `inventory.patch` callback.
- Conventions already in use by the owner's POS (moyun-pos), which our importer must understand: SKU `custom_fields.code` (menu code such as "A2"), `custom_fields.vat_category` (food, beverage, zero_rated, out_of_scope), `custom_fields.translations.{fr,en,nl,zh}.{name,description}`, category `description` as JSON `{"translations":{"fr":..,"en":..,"nl":..,"zh":..}}`, one POS item per SKU, option keys `sku|list|option`, channel key lower-cased (`webshop` when absent) matched against a `hubrise_channels` table, cash payment refs table to decide prepaid versus unpaid.

## 3. Architecture

### 3.1 Module layout

```
pkg/hubrise/                       HTTP client + API types (like pkg/apns, pkg/fcm)
  client.go  types.go  money.go  oauth.go  errors.go  ratelimit.go
  hubrisetest/                     Go mock HubRise server (httptest) + fixtures (like pkg/apns/apnstest)
internal/modules/hubrise/
  domain/          Connection, CatalogLink, OutboxItem, Event, status mapping, neutral Catalog, repository ports
  application/     ConnectionService (oauth, settings, disconnect), CatalogImporter (plan/apply),
                   InventoryService, OrderPusher (payload builder + enqueue), OutboxWorker,
                   EventProcessor, StatusSync, Reconciler, Hooks (consumer-facing facade), ports
  infrastructure/  sqlx repositories (Admin pool), tokencrypt (AES-256-GCM), clock
  interfaces/      gin handlers: POST /hubrise/callback, GET /hubrise/oauth/callback
cmd/app/hubrise.go                 composition root helper (initHubrise), excluded from coverage like all of cmd/
```

Dependency rule as everywhere: interfaces -> application -> domain <- infrastructure. The hubrise module does **not** import other business modules directly. It declares ports (`OrderReader`, `UserReader`, `CatalogWriter`, `OrderTransitioner`, `ProductGuardTarget`...) implemented by thin adapters in `cmd/app/hubrise.go` or in the resolver package, which is where cross-module orchestration already lives (compare `NewOrderNotifier` in payment/interfaces).

### 3.2 Hooks: how core code calls into HubRise with zero cost when absent

The resolver package gets one optional field `Resolver.Hubrise HubriseHooks` (nil in standalone). Consumer-defined interface, all methods nil-safe through tiny helpers:

| Hook | Called from | Effect |
|---|---|---|
| `OrderReady(ctx, orderID)` | `CreateOrder` (cash orders) and the Mollie paid branch, the latter through a small nil-safe `OrderReadyHook` port added to the `PaymentHandler` constructor (the payment package never imports resolver or hubrise; `main` passes an adapter) | idempotent enqueue of `order_create` |
| `OrderStatusChanged(ctx, orderID, newStatus)` | `orderService.UpdateOrder` through an optional `StatusObserver` port (single chokepoint, covers the GraphQL mutation, `HandlePaymentFailed` and POS paths); skipped when the context carries the HubRise origin marker | enqueue `order_status` |
| `AvailabilityChanged(ctx, productID, available)` | `UpdateProduct` / MCP path when `isAvailable` changed | enqueue `inventory` |
| `ProductGuard.CheckUpdate(ctx, old, new)` | product service `UpdateProduct`, choice and group mutations | reject edits of HubRise-owned fields |

When the installation is not configured, `Hubrise` is nil and no HubRise code runs. When it is configured but the runtime switch is off, every hook returns after one read of the `hubrise_connection` row (a primary key read, not cached: a cache would let the hooks queue rows for a while after a disable, and a settings change on one replica is invisible to the cache of the other). No row is queued once the switch is off, and workers also re-read `enabled` (and the feature toggles) inside the claim statement itself, so a disable takes effect on the next claim on every replica.

### 3.3 Two-level opt-in (standalone switch)

1. **Deployment level.** HubRise is *available* only when `HUBRISE_CLIENT_ID`, `HUBRISE_CLIENT_SECRET` and `HUBRISE_TOKEN_KEY` are all set. Otherwise: module not constructed, routes not registered, workers not started, GraphQL admin API answers `available: false`. A deployment that never sets them (every existing one, on day one) is byte-for-byte unchanged apart from additive migrations.
2. **Runtime level.** `hubrise_connection` single row. Not connected = standalone. Connected with `enabled = false` = paused, nothing leaves, nothing is imported, locks are released, links and the outbox are kept. Four feature toggles on top: `push_orders`, `sync_status`, `sync_inventory`, `sync_catalog` (catalog direction IMPORT, the mode named `hubrise` in the first draft). A15 adds the fifth, `publish_catalog` (catalog direction PUBLISH), mutually exclusive with `sync_catalog`: the catalog direction is NONE, IMPORT or PUBLISH.

Toggling is lossless: disabling never deletes links or products; re-enabling re-adopts the same rows. "Connected" means `access_token_enc IS NOT NULL`. "Disconnect" revokes the token at HubRise, deletes the callback, sets `access_token_enc = NULL` and `enabled = false` (the row, its settings and ids stay), keeps links unless `forgetLinks: true` (products stay either way, they simply become ordinary local products).

Re-enabling push is not a replay: `push_orders_since` is stamped every time order pushing becomes effective (connect, `enabled` false to true, `push_orders` false to true), and the reconciler only ever considers OPEN orders created after `push_orders_since - 1 h` (the 1 h grace covers orders in flight at connect time). Terminal orders are never auto-pushed, so a toggle cannot flood the EPOS with history or reprint kitchen tickets. A reconnect to a different HubRise location or catalog is detected and blocked (section 5.5).

### 3.4 Workers (all in-process, started from main when available)

| Worker | Cadence | What it does |
|---|---|---|
| Outbox drain | wake-up channel (an optimisation only) + 5 s tick | claims due rows (`FOR UPDATE SKIP LOCKED`, per-order FIFO, claim statement increments `attempts`, sets the lease and re-checks `enabled`/toggles), sends them, backoff 30 s doubling to 30 min, parks permanent refusals (section 6.1) |
| Event processor | wake-up channel + 5 s tick | claims `pending` callback events, applies them idempotently |
| Reconciler | 2 min, lease-guarded | (a) enqueue OPEN orders created after `push_orders_since - 1 h` that became actionable but have no `hubrise_orders` row (crash between commit and enqueue), (b) status safety net: for orders with a `sent` link whose local status differs from `last_remote_status` and no pending `order_status` row, enqueue the missing PATCH (covers any writer that bypassed the observer, and lost rows), (c) refresh at most 5 open pushed orders per run with `GET /location/orders/:id` (oldest refresh first), (d) flag orders still `new` at HubRise after 5 min, (e) purge old events and foreign-order cache |
| Catalog drift | 6 h, plus every 30 s a check for `catalog` events older than 30 s (debounce is DB backed: events carry `received_at`, all due ones collapse into one import) | fetch catalog, compare content hash, import if changed (never auto-applies a mass retire, section 5.5) |
| Inventory full sync | 30 min and on `inventory` events | `GET /location/inventory`, apply |
| Callback poller | 10 min | `GET /callback/events` to pick up events HubRise could not deliver, then ack |
| Sold-out expiry sweeper | 1 min, lease-guarded | stock-0 entries whose `expires_at` passed become available again (only links with `inventory_sold_out = true`) |

Singleton jobs take a row in `hubrise_job_leases (name PRIMARY KEY, holder, leased_until)` with `UPDATE ... WHERE leased_until < now()` (compare-and-set, renewed while running), so correctness does not depend on which pooled connection runs which statement. All workers use an admin context and stop on shutdown (same pattern as the existing purge and sweeper goroutines in `main.go`).

**Rate budget** (HubRise limits: 500/min, 2,500/h, 10,000/day per connection; only `GET /catalogs/:id` and the order LIST endpoint `GET /orders`, which includes `?private_ref=` lookups, are also capped at 10/min; single-order retrieval `GET /orders/:id` is not in that bucket). The client limiter enforces all four windows with headroom (default ceilings 400/min, 2,000/h, 8,000/day) and splits the 10/min list bucket by priority: 6/min reserved for order lookups (idempotency), 3/min for catalog reads, 1 spare. Two classes of caller: `order-critical` (create, status PATCH, private_ref lookups, inventory PATCH) which may use the whole hourly/daily budget, and `background` (reconciler refresh, drift, inventory poll, callback poller) which is cut off at 60 % of the hourly and daily ceilings. The reconciler never lists orders: it refreshes at most 5 single orders per run. After an outage, only rows that were already claimed before (possibly sent) need a lookup, so a 100 order backlog drains in about 17 min without ever starving the catalog drift check; this is asserted by a limiter test.

## 4. Database changes (all additive, expand only)

Principles: no table rewrite, no long lock, no data destroyed, every migration has a working `Down`.

- Each migration that touches an existing table starts with `SET LOCAL lock_timeout = '5s'`. Goose wraps a file in one transaction, so `lock_timeout` only bounds lock ACQUISITION: a busy table makes the migration fail fast instead of queueing every writer behind an ACCESS EXCLUSIVE request. A failed migration makes `tsb-migrate` exit non-zero and fails the deploy job BEFORE any pod rolls (the migration runs in a pre-upgrade Helm hook of tsb-infra, see A10), so the old pods keep serving untouched and the deploy is simply re-run. A test holds an open transaction with a row lock on `orders` and asserts the migration errors out within the timeout without waiting.
- `ADD COLUMN ... NOT NULL DEFAULT <constant>` and nullable `ADD COLUMN` are metadata-only on PostgreSQL 11+ (prod is far above). **No CHECK constraints are added to existing tables** (review decision): `ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT` inside one goose transaction would hold the ACCESS EXCLUSIVE lock through the validation scan, which is exactly what must not happen on `orders`. Values of `orders.channel` and `*_translations.source` are validated in Go (domain constants) instead. New tables (all empty at creation) may carry CHECKs freely.
- No `CREATE INDEX` on big existing tables.
- **Version ordering.** Every HubRise migration has a strictly increasing timestamp in task order (below) and later than anything on main, so an environment that already applied an earlier task's migrations (the test server deploys on every push to main) never meets a "missing" lower version. A test applies all migrations in order on a clean database, then asserts goose reports no missing versions (`goose.WithAllowOutofOrder(false)`) and that every HubRise migration is newer than the newest pre-HubRise one.
- `cmd/migrate` runs BEFORE the new pods roll out in the production deploy flow: a pre-upgrade Helm hook in tsb-infra runs the `tsb-migrate` binary of the NEW image against the database, then `helm upgrade --atomic` rolls the pods. The old pods therefore serve on the NEW schema for the length of the rollout, which is why every migration is additive and why no production query may depend on the column set of a table (see A10).

Considered and **rejected** restructurings (and why):

- *Shared option lists as a first-class table.* HubRise option lists are shared across SKUs; ours are per product (`product_choice_groups.product_id`). Making them shared would change the GraphQL shape (`ProductChoiceGroup.productId`, `choices`), the order FKs, the dashboard editor and the apps already in the stores. Instead the importer **materializes one local group per (SKU, option list)**, linked by key `sku|list`. Cost: duplication of rows. Benefit: zero client change.
- *Splitting product and SKU.* Local products have a single price; a HubRise product with several SKUs becomes several local products named "Product - SKU" (same as moyun-pos, one item per SKU).
- *Unique constraint on `products.code`* or making `code` mandatory: not needed.
- *Moving HubRise columns onto core tables* (`products.hubrise_ref`...): rejected in favour of one link table so core tables stay HubRise-free and standalone installs carry nothing. The only core-table additions are the three listed below.

Migration order (task order = timestamp order):

### M1 `20261024120000_create_hubrise_connection.sql` (T1)

- `hubrise_connection`: `id BOOLEAN PRIMARY KEY DEFAULT TRUE CHECK (id)` (single row, same idiom as `restaurant_config`), `enabled BOOLEAN NOT NULL DEFAULT FALSE`, **`access_token_enc BYTEA NULL`** (AES-256-GCM, 1 version byte + 12 byte nonce + ciphertext; NULL = disconnected), `account_id, account_name, location_id, location_name, catalog_id, catalog_name, customer_list_id TEXT`, `scope TEXT`, feature toggles `push_orders, sync_status, sync_inventory, sync_catalog BOOLEAN NOT NULL DEFAULT FALSE` (all off, see A12), `auto_refund_on_cancel BOOLEAN NOT NULL DEFAULT FALSE`, `catalog_language TEXT NOT NULL DEFAULT 'fr'` (CHECK in fr,en,nl,zh), `variant_ref TEXT`, `channel_name TEXT`, `delivery_charge_ref, payment_fee_charge_ref TEXT`, `import_images BOOLEAN NOT NULL DEFAULT FALSE`, `catalog_hash TEXT`, `catalog_preview_hash TEXT`, `catalog_preview_at TIMESTAMPTZ` (a successful DRY_RUN; required before `sync_catalog` can be turned on, section 5.4), `push_orders_since TIMESTAMPTZ`, `inventory_baseline_at TIMESTAMPTZ` (section 8), `relink_required_at TIMESTAMPTZ` (section 5.5), `last_catalog_sync_at, last_event_at, auth_error_at TIMESTAMPTZ`, `last_error TEXT`, `callback_registered_at`, `created_at, updated_at`.
- `hubrise_oauth_states (state TEXT PRIMARY KEY, admin_user_id UUID NOT NULL, created_at, expires_at)` for the OAuth `state` nonce (one-time, 10 min).
- `hubrise_job_leases (name TEXT PRIMARY KEY, holder TEXT NOT NULL, leased_until TIMESTAMPTZ NOT NULL)`.
- Backfill: none. Tables start empty; absence of a row = not connected = standalone. Down: drop the tables.

### M2 `20261024130000_create_hubrise_catalog_links.sql` (T1)

`hubrise_catalog_links`: `id BIGSERIAL PK`, `entity_type TEXT CHECK in (category, product, choice_group, choice)`, four nullable FK columns `category_id -> product_categories`, `product_id -> products`, `choice_group_id -> product_choice_groups`, `choice_id -> product_choices`, **all `ON DELETE CASCADE`** (deleting a choice in the dashboard cleans its link), a CHECK that exactly the column matching `entity_type` is non-null, `hubrise_key TEXT NOT NULL` (category: ref; product: SKU ref; group: `skuRef|listRef`; choice: `skuRef|listRef|optionRef`), `hubrise_ref TEXT NOT NULL` (last segment; the option ref is what inventory entries name), `hubrise_id TEXT`, `content_hash TEXT NOT NULL DEFAULT ''`, `origin TEXT CHECK in (import, adopted, manual)`, `stock NUMERIC(12,3)`, **`inventory_sold_out BOOLEAN NOT NULL DEFAULT FALSE`** (true only while this link's unavailability was caused by HubRise inventory; the provenance marker of section 8), `sold_out_until TIMESTAMPTZ`, **`catalog_disabled BOOLEAN NOT NULL DEFAULT FALSE`** (HubRise restrictions say disabled; effective availability of a managed row = `NOT catalog_disabled AND NOT inventory_sold_out`), `inventory_synced_at`, `image_md5 TEXT`, `retired_at TIMESTAMPTZ`, timestamps. Partial unique indexes per FK column (one link per local row) and `UNIQUE (entity_type, hubrise_key)`; index on `(entity_type, hubrise_ref)` for inventory lookups.
Backfill: none (no links until the owner runs adoption). Down: drop table.

### M3 `20261024140000_create_hubrise_orders_outbox_events.sql` (T1; was M6 in the first draft)

- `hubrise_orders`: `order_id UUID PRIMARY KEY REFERENCES orders ON DELETE CASCADE`, `hubrise_order_id TEXT` (unique where not null), `push_state TEXT CHECK in (pending, sent, parked, skipped)`, `pushed_at`, `last_remote_status TEXT`, `last_remote_event_at TIMESTAMPTZ` (set ONLY from remote event or remote GET data), `last_local_patch_at TIMESTAMPTZ` (set when we send a status PATCH), `remote_total NUMERIC(10,2)`, `needs_attention TEXT`, timestamps. This table is also the idempotency anchor for `order_create`: enqueue is `INSERT INTO hubrise_orders ... ON CONFLICT (order_id) DO NOTHING` and the outbox row is inserted in the same transaction only when the insert happened.
- `hubrise_outbox`: `id BIGSERIAL PK`, `kind TEXT CHECK in (order_create, order_status, inventory)`, `order_id UUID REFERENCES orders ON DELETE CASCADE NULL`, `dedupe_key TEXT`, `payload JSONB NOT NULL DEFAULT '{}'`, `state TEXT CHECK in (pending, sending, sent, parked, skipped) DEFAULT pending`, `attempts INT NOT NULL DEFAULT 0` (number of claims), `leased_until TIMESTAMPTZ`, `next_attempt_at TIMESTAMPTZ DEFAULT now()`, `last_error TEXT`, `created_at, sent_at, parked_at`. Partial unique index `(dedupe_key) WHERE state = 'pending' AND kind = 'inventory'` (inventory rows collapse to the latest pending state; a row already `sending` is excluded, so a newer toggle creates a fresh row and is never lost). `order_status` rows are NOT deduplicated (section 7.1). Index `(state, next_attempt_at)`, index `(order_id, id)`.
- `hubrise_events`: `id TEXT PRIMARY KEY` (HubRise event id), `resource_type, event_type TEXT`, `payload JSONB NOT NULL`, `received_at`, `run_after TIMESTAMPTZ`, `state TEXT CHECK in (pending, done, failed, ignored)`, `attempts INT`, `next_attempt_at`, `processed_at`, `last_error`.
- `hubrise_foreign_orders (hubrise_order_id TEXT PRIMARY KEY, seen_at TIMESTAMPTZ)`: cache of HubRise orders known not to be ours (placed by other channels), purged after 7 days, so the processor never re-fetches them.
- Backfill: none. Down: drop the tables.

### M4 `20261024150000_add_translation_source.sql` (T4)

`source TEXT NOT NULL DEFAULT 'manual'` on `product_translations`, `product_category_translations`, `product_choice_translations`, `product_choice_group_translations`. No CHECK (validated in Go: `manual` | `hubrise`). Each of the four ALTERs sits behind `SET LOCAL lock_timeout`.
Backfill: the default **is** the backfill: every existing row is correctly `manual` (nothing ever came from HubRise). Down: drop the columns (loses provenance only).
Code change that goes with it: the dashboard's translation upsert must keep `source = 'manual'` only when the text actually changed:
`ON CONFLICT ... DO UPDATE SET name = EXCLUDED.name, description = EXCLUDED.description, source = CASE WHEN (t.name, t.description) IS DISTINCT FROM (EXCLUDED.name, EXCLUDED.description) THEN 'manual' ELSE t.source END`.

## 5. Catalog: HubRise as source of truth

### 5.1 Ownership model

There are two mutually exclusive modes (A15). In **IMPORT** mode HubRise owns the menu and the table below applies. In **PUBLISH** mode the dashboard (the local database) owns the whole menu: nothing is locked, `HUBRISE_MANAGED` is never raised, and every field below flows local -> HubRise (A15 lists the exact mapping and the fields left to HubRise). With neither mode on, nothing is owned by HubRise and nothing is published.

IMPORT mode: for a product that has a link row *and* `sync_catalog` on *and* `enabled`:

| Field | Owner | Dashboard edit |
|---|---|---|
| price, category, vat_category, code (when HubRise has one), choice groups and choices (names, prices, min/max) | HubRise | rejected with `HUBRISE_MANAGED` |
| name and description in `catalog_language` | HubRise unless overridden | allowed; the edit flips `source` to `manual` and survives re-imports |
| translations in the other languages | local (HubRise is mono-language) | allowed, never touched by the importer |
| is_halal, is_vegetarian, is_spicy, is_lunch_only, is_discountable, piece_count, image | local | allowed (tags only seed them at creation) |
| is_visible | HubRise sets it at creation / on enable-disable; local toggle allowed | allowed |
| is_available | inventory, two-way (section 8) | allowed, pushed to HubRise |

With the integration off, `sync_catalog` off or disconnected, **nothing is locked**: the guard is a no-op and managed products become plain local products again.

### 5.2 Translations survive re-imports

HubRise names live in `catalog_language` (default `fr`, the authoring language). The importer upserts a translation row only if it is missing or `source = 'hubrise'`; a `manual` row is never overwritten. Languages not present in HubRise are never written. If the HubRise data uses the owner's existing conventions (`custom_fields.translations`, category `description` JSON), those languages are written with `source = 'hubrise'` too. Products with a single translation stay valid: the read path already falls back through `translationFallbackOrder` (fr first). The domain rule "visible product needs 3 translations" lives in `NewProduct` only; the importer writes through its own repository method and does not call it, so imported products are visible with one language.

### 5.3 Mapping rules

- **Category**: every HubRise category that directly holds products becomes a local category (the tree is flattened, parents without products are ignored). Name from HubRise in `catalog_language`; `order` from depth-first catalog order; **slug generated once** (gosimple/slug of the name, `-2` suffix on collision) and never regenerated, because slugs are public URLs (`productCategoryBySlug`).
- **Product**: one local product per SKU. Name = product name, plus " " and the SKU name when the product has several SKUs or the SKU is named. Price = SKU price, after `price_overrides` for the configured `variant_ref` (last matching rule wins; rules with time or date windows are ignored in v1 and reported). Product slug uses the existing rule (category fr name + product fr name) through a shared function; `ErrDuplicateProductName` is resolved with a numeric suffix.
- **Code**: SKU `custom_fields.code` (kept only if present; an existing local code is never blanked).
- **VAT**: `custom_fields.vat_category` wins. Otherwise from `tax_rate`: collection and eat_in `6/12` -> food, `21/21` -> beverage, all `0` -> zero_rated. Anything else is **unmappable**: the product is created with `is_visible = false` and listed in the import report as `VAT_UNMAPPED`, because VAT drives invoices and fiscal rules.
- **Visibility**: SKU `restrictions.enabled = false`, tag `hidden` or tag `web:hidden` -> `is_visible = false` (on create and on change of the HubRise side). Time windows, day-of-week and per-customer restrictions are ignored in v1 (reported).
- **Option lists**: for each (SKU, option list) a local group keyed `sku|list`. `min_selections` from HubRise, `max_selections` null -> number of options (or 99 when `multiple_selection`), 0 -> the same. Options -> choices keyed `sku|list|option`, `price_modifier = max(price, 0)` (local CHECK forbids negatives; a negative HubRise price is reported), `sort_order` from list order. Option `restrictions.enabled = false` -> `is_available = false`.
- **Deals, discounts, charges, nutrition, barcodes**: not imported in v1. Charge refs for delivery and online fee are configurable strings used by the order push.
- **Removed from HubRise**: link gets `retired_at`, product becomes `is_visible = false, is_available = false`. Never deleted. If the SKU reappears, the same product is revived.
- **Images** (opt-in `import_images`): download `GET /catalogs/:id/images/:id/data`, upload through `utils.UploadProductImage` keyed by product UUID, only when the MD5 differs from `image_md5`. Failures are non-fatal.

### 5.4 Import is a plan, then an apply (adoption)

Production already has a populated menu. Turning on catalog sync must not duplicate it. The importer therefore has two phases and three modes:

- `Plan(catalog) -> Diff`: pure function over (HubRise catalog, local state, links). Lists `create`, `update`, `link` (adoption), `retire`, `warnings`, `conflicts`. No writes.
- `Apply(diff)`: one transaction per category-batch, under `pg_advisory_xact_lock`, idempotent (content hash per link; unchanged items cost no write).
- Modes: `LINK_ONLY` (match and create link rows only; used to give an existing menu its SKU refs for order pushing without touching any product data), `FULL` (adopt, create, update, retire), `DRY_RUN` (return the Diff).
- Adoption matching order: explicit manual link; `custom_fields.code` equal to `products.code`; normalized fr name within the same-named category. Anything ambiguous or unmatched is reported, never guessed.

Publishing: each changed product emits the existing `productUpdated` PubSub event so dashboards refresh.

Safety rules that live in the application service (T4), so T8 only wires them:

- **Preview before enabling.** `sync_catalog` can be turned on only if a successful `DRY_RUN` of the current `catalog_hash` was recorded in the last 24 h (`catalog_preview_hash` / `catalog_preview_at`). Otherwise `HUBRISE_PREVIEW_REQUIRED`.
- **Empty-catalog refusal**: a catalog with zero products is rejected.
- **Mass-retire threshold** (see 5.5): the plan refuses to retire more than 30 % of the linked, non-retired products (and at least 5) unless the caller passes `confirmRetire: true`. Scheduled drift imports never carry that confirmation: when the threshold trips they apply nothing, store the diff summary in `last_error` / the status `pendingReview` flag and wait for a human.

### 5.5 Reconnecting to a different location or catalog

Links name refs of one specific HubRise catalog. On the OAuth callback the new `location_id` / `catalog_id` are compared with the stored ones. If they differ and `hubrise_catalog_links` is not empty, the connection is saved with `enabled = false`, `sync_catalog = false`, `sync_inventory = false` and `relink_required_at = now()`; `updateHubriseSettings(enabled: true)` is then refused with `HUBRISE_RELINK_REQUIRED` until the owner clears the old links (`forgetHubriseLinks` mutation, or `disconnectHubrise(forgetLinks: true)` before reconnecting). Pushing orders with stale `sku_ref`s and retiring a whole menu against a foreign catalog are therefore both impossible. The mass-retire threshold above is the second line of defence.

## 6. Pushing orders

### 6.1 Flow

`OrderReady` -> one transaction: `INSERT INTO hubrise_orders (order_id, push_state='pending') ON CONFLICT DO NOTHING`, and only if a row was inserted, insert the `order_create` outbox row -> drain worker POST -> `hubrise_order_id` stored, `private_ref` = local order UUID. A redelivered Mollie webhook (or a double call) hits the primary key and enqueues nothing (test: paid webhook delivered 3 times yields exactly one outbox row).

**Snapshot at enqueue, status and refs at send time.** Because `order_product` does not snapshot names or base prices (section 2), the item data (names, base prices, option modifiers, tax rate, charges, discounts, customer, notes) is captured into the outbox payload in the enqueue transaction, so a price edit seconds later cannot change what the kitchen sees. Two parts are resolved by the worker right before the POST: `sku_ref` / `option ref` (from the link table, so an adoption done meanwhile is picked up) and the initial status. The initial `status` is the order's CURRENT local status mapped to HubRise (so an order that staff already moved to CONFIRMED / PREPARING / AWAITING_PICK_UP while the push was waiting or backing off is created in that state, never as a stale `new`). To keep this consistent with queued status rows, the worker reads, in this order and in one short transaction, (1) the highest pending `order_status` outbox id for the order, then (2) the current local status; after a successful POST the pending `order_status` rows with `id <= (1)` are marked `skipped` (their transitions are covered by the create) and `last_remote_status` is set. Rows enqueued after (1) stay queued and are sent as PATCHes in order.
If, at send time, the order is already terminal and was never sent (CANCELLED, FAILED, DELIVERED, PICKED_UP), the create is marked `skipped` (HubRise never sees an order the shop has already finished; nothing is reprinted).

**Claiming and leases.** The claim is one statement: `UPDATE hubrise_outbox SET state = 'sending', attempts = attempts + 1, leased_until = now() + interval '5 minutes' WHERE id IN (SELECT ... WHERE state = 'pending' AND next_attempt_at <= now() AND <FIFO rule> AND connection enabled and toggle on FOR UPDATE SKIP LOCKED) RETURNING ...`. `attempts` is therefore durable before the HTTP call, so a crash between send and acknowledgement is recognised on the next claim (`attempts > 1`, or a `sending` row whose lease expired and is reclaimed) and the worker first runs the idempotency lookup `GET /location/orders?private_ref=<uuid>`; if the order exists it is adopted (store `hubrise_order_id`, mark sent) instead of being POSTed again. Completion is `UPDATE ... SET state = 'sent' WHERE id = $1 AND state = 'sending'`. The lease is renewed before each row of a batch (`Extend`, which fails once the lease ran out, in which case the row is left alone for the next claim) and is at least four times the per-call timeout, so another replica cannot reclaim a row that is still being sent. A row in `sending` is outside the inventory dedupe index, so a toggle arriving mid-send inserts a fresh pending row instead of being merged into the in-flight one and lost.

**FIFO rule per order.** A row is claimable only if the same order has no earlier row in `pending`, `sending` or `parked` (a parked create blocks everything behind it, so a PATCH is never sent for an order HubRise never received). Inventory rows are FIFO per `dedupe_key`.

**Outcome classification.**

| Outcome | Behaviour |
|---|---|
| 2xx | sent |
| 401, 403 (revoked token, unpaid account, missing scope, location disabled: all connection-level at HubRise) | pause the pipeline: `auth_error_at` + `last_error`, the claim's `attempts` increment is reverted, nothing is parked, banner in the dashboard status and Sentry; reconnect clears it |
| 400, 422 | park the row with the HubRise message (the payload is wrong, retrying cannot help); a manual retry reactivates the WHOLE parked chain of that order |
| 404 on a status PATCH or on a lookup of a known id | do not park: re-verify through `private_ref`; if HubRise knows the order under another id, backfill `hubrise_order_id` and retry; if it does not know it, reset `hubrise_orders` to `pending` and re-enqueue the create once (the rest of the chain waits behind it); a second 404 parks |
| 429, 5xx, timeout | retry with backoff 30 s doubling to 30 min |

**Max age per kind.** `order_create` 48 h then parked and flagged. `order_status` 6 h then `skipped` (the reconciler diff re-enqueues the right PATCH if the order is still open and the link is `sent`); an `order_status` or `inventory` row whose order has no `hubrise_order_id` and whose create is parked or skipped is `skipped` immediately. `inventory` 24 h. After a pause or a disable of several days, stale rows are therefore aged out, not replayed (test: re-enable after 3 days).

**Catch-up guarantee.** The enqueue happens after the order commit, so a crash between the two would lose the push. The reconciler enqueues any OPEN, actionable order (not pending payment, not test, not failed, not terminal) created after `push_orders_since - 1 h` that has no `hubrise_orders` row. It never enqueues terminal orders and never uses the connection row's `created_at`, so neither a toggle nor a reconnect can replay history. The same reconciler status diff (section 3.4 (b)) is the safety net if the status observer ever misses a transition.

### 6.2 Payload mapping

| HubRise field | Value |
|---|---|
| `private_ref` | order UUID |
| `ref` | short human reference (first 8 chars of the UUID, uppercase) |
| `channel` | `connection.channel_name`, else `orders.channel` (`web`/`app`), else `webshop` |
| `status` | current local status mapped to HubRise at send time (`new` for a fresh order), section 6.1 |
| `service_type` | PICKUP -> `collection`, DELIVERY -> `delivery` |
| `expected_time`, `asap` | `preferred_ready_time` (Europe/Brussels offset) else `asap: true` |
| `customer` (guest order) | first/last name, email, phone from the user; for delivery address_1 (street + number + box), postal_code, city, country `BE`, lat/lng, `delivery_notes` = address_extra. Sent only when the order carries no `customer_id` (amendment A1, section 19: a registered user's order names its customer list entry instead, never both) |
| `customer_notes` | order note + order extras (chopsticks, sauces), cash amount to prepare change for |
| `coupon_codes` | coupon code |
| `items[]` | `product_name` (fr name), `sku_name`, `sku_ref` (link; item still sent without a ref if unlinked, and the order is flagged `needs_attention = UNLINKED_ITEM`), `price` = **base** SKU price, `quantity`, `tax_rate` = stored `vat_rate_applied` as a percent decimal 0 to 100 (HubRise format, e.g. `"6"`, not a ratio), `options[]` |
| `charges[]` | delivery fee (`ref` = configured delivery charge ref), online payment fee (`PAYMENT_FEE`) |
| `discounts[]` | pickup discount (`TAKEAWAY`), coupon discount (coupon code); amounts are positive `price_off` Money strings as in the moyun-pos `order_create_doc` fixture |
| `payments[]` | online: one entry `{name: "Mollie", ref: "MOLLIE", amount: total, info: {mollie_payment_id}}` (the `type` field is deprecated at HubRise and not sent); cash: none (unpaid), so the EPOS collects. Name/ref values are checked against the moyun-pos fixtures and open question 5 |

HubRise CALCULATES `total` (items + charges - discounts, per the API docs); the mock does the same, and the response's `total` is compared with the local total: a mismatch sets `needs_attention = TOTAL_MISMATCH` |

Options: base price is recomputed as `(line total - sum(modifier x selection qty)) / qty` only as a cross check; the payload uses today's product base price and choice modifiers read at enqueue time (negative modifiers clamped to 0, as `PriceLine` does). Selection quantities are totals for the line: if every selection quantity is divisible by the line quantity, send `quantity = q` and per-unit option quantities; otherwise split the line into `q` single-unit items with the selections distributed as evenly as possible (totals stay exact). This is documented as an approximation for the kitchen ticket in tests.

HubRise-side edits to items of an order (EPOS deleting or adding items) are **not** applied in v1; the remote `total` is stored in `hubrise_orders.remote_total` and a difference sets `needs_attention`.

## 7. Status back to tsb-service

### 7.1 Mapping

| HubRise | Local effect |
|---|---|
| `new`, `received` | none (store `last_remote_status`) |
| `accepted` | CONFIRMED |
| `in_preparation` | PREPARING |
| `awaiting_collection` / `awaiting_shipment` | PICKUP: AWAITING_PICK_UP. DELIVERY: no change (a "ready for pickup" email would be wrong for a delivery) |
| `in_delivery` | OUT_FOR_DELIVERY |
| `completed` | PICKUP: PICKED_UP, DELIVERY: DELIVERED |
| `cancelled`, `rejected` | Unpaid / cash orders: CANCELLED (reason `OTHER`) through the full cancel path (coupon rollback, notifications). **Online-paid orders: depends on `auto_refund_on_cancel`** (default `false`, an owner decision, open question 10): when off, nothing moves money; the order is left as is, `needs_attention = REMOTE_CANCELLED_PAID` is set, staff and Sentry are alerted, and staff confirm by cancelling in the dashboard (which runs the existing refund path; the matching outbound PATCH is skipped because `last_remote_status` is already `cancelled`). When on, the same full cancel path runs automatically: Mollie refund / payment cancel under the payment advisory lock, refund email, coupon rollback. An EPOS mis-tap or auto-reject rule can never refund money by default. |
| `delivery_failed` | no automatic change; `needs_attention = DELIVERY_FAILED`, Sentry event. Staff decide (refund policy) |
| `confirmed_time` changed | `estimated_ready_time` updated (existing "ready time updated" notification). "Changed" is against `hubrise_orders.last_remote_confirmed_time`, the value last seen at HubRise: local ready time edits are never pushed back, so an unchanged remote value must not reset them |

Reverse (local to HubRise): CONFIRMED -> `accepted`, PREPARING -> `in_preparation`, AWAITING_PICK_UP -> `awaiting_collection`, OUT_FOR_DELIVERY -> `in_delivery`, PICKED_UP / DELIVERED -> `completed`, CANCELLED -> `cancelled`. PENDING and FAILED are never pushed (FAILED orders were never actionable). Both sides can change status (the dashboard and the EPOS); last event wins, with the guards below.

- **Enqueue rule.** `StatusObserver.OrderStatusChanged` (called from `orderService.UpdateOrder`, section 3.2) enqueues an `order_status` row for any order whose `hubrise_orders.push_state` is `pending` OR `sent` (a transition during an outage or backoff is no longer lost). Rows follow the per-order FIFO of section 6.1, so they wait behind the `order_create`; if the create goes out first with the then-current status, the covered rows are `skipped`.
- **No collapsing dedupe.** Each local transition gets its own row (`dedupe_key = order:<uuid>:status:<order_status_history id>`, unique per transition), with the TARGET status frozen in the payload. A sequence CONFIRMED -> PREPARING -> CONFIRMED is sent as three PATCHes in order; it is not collapsed by a "same status pending" key. A PATCH whose target equals `last_remote_status` is skipped as a no-op.
- **Writers audited.** T3 greps every writer of `orders.order_status` (see section 2) and adds a characterization test per path: GraphQL `UpdateOrder`, `UpdatePaymentStatus` -> service, `HandlePaymentFailed` (cancelled/failed/expired webhook), POS endpoints, MCP paths, and `CancelStaleTestOrders` (asserted NOT to enqueue: test orders are never pushed).

### 7.2 Safe application of inbound events

We register only the events we use (`order: [update]`, `catalog: [create, update, delete]`, `inventory: [update, patch]`; the names HubRise documents). A `POST /callback` with any other combination is a 422 at HubRise, so the Go mock rejects unknown combinations too and the registration test pins the exact body. `order.create` is not registered (orders created by other channels are irrelevant); if one ever arrives it is stored as `ignored` without any API call.

1. Callback handler: verify HMAC (`X-HubRise-Hmac-SHA256`, hex HMAC-SHA256 of the raw body keyed with the client secret, constant time), reject mismatched `location_id`, insert into `hubrise_events` (`ON CONFLICT DO NOTHING` = idempotency), wake the processor, answer 200 immediately. Nothing else happens in the request.
2. Processor lookup of the local order: by `hubrise_order_id`. If unknown:
   - if the order is in the foreign-order cache: ignore, no API call;
   - **race with our own push:** if any `order_create` outbox row is `pending`/`sending`, or a `hubrise_orders` row is `pending` with no `hubrise_order_id` and was claimed within the last 10 minutes, the event is DEFERRED (state stays `pending`, `next_attempt_at` +15 s growing, for up to 10 minutes), never ignored, because the answer to our POST may not be stored yet or may have been lost;
   - otherwise `GET /location/orders/:id` (single retrieval, not in the 10/min list bucket; at most 60 such GETs per minute, further events are deferred). The fetched `private_ref` is the authoritative match: if it names a local order, `hubrise_order_id` is backfilled and the event proceeds; if not, the order id goes into `hubrise_foreign_orders` and the event is `ignored`.
3. Ordering guard (clocks differ, HubRise timestamps have second precision and our own PATCHes generate no event for our client): `last_remote_event_at` is set only from remote data. When the event `created_at` is not strictly newer than it, equals it, falls within 5 s of `last_local_patch_at` for that order, or `new_state` is missing, the processor does not trust the event payload: it re-reads `GET /location/orders/:id` and applies the status found there (authoritative). Older strictly-stale events with no such ambiguity are ignored.
4. While a `pending` or `sending` `order_status` outbox row exists for the order, the local status is ahead of HubRise: the event (or reconciler read) waits (event deferred 15 s) instead of moving the order back; once the PATCH has gone out the guard above re-reads next to it. Idempotent: mapped status equal to current status is a no-op. Terminal local statuses (CANCELLED, FAILED, DELIVERED, PICKED_UP) are never moved back by a non-terminal remote status (logged, flagged).
5. Apply through the shared transition method (task T3) with the HubRise origin marker in the context, so emails, APNs/FCM, Live Activity, `orderUpdated` PubSub and coupon rollback behave exactly as for a dashboard change, and the observer does not queue an echo PATCH.
6. Failure (for example `ErrPaymentNotRefundable` on cancel) leaves the order untouched, the event `failed` with backoff, and the order flagged for staff.

Callback endpoint rate limiting (section 9): requests with a valid signature are never rate limited, so HubRise retry bursts cannot get 429 and lose events.

As built (T6):

- **Endpoint.** `interfaces.CallbackHandler` serves `POST /hubrise/callback` (T9 mounts it under `/api/v1` when the module exists). A bad or missing signature is 401 and is the only thing counted by the failed-verification limiter (30 a minute per `c.ClientIP()`, 429 beyond); a signed body that is not an event is 400, a signed event of another location 403, an installation that never connected 404, a storage failure 500 (HubRise retries it). A paused connection (disabled, auth error, relink) is answered 200 and the event is dropped: the reconciler refresh and the drift checks catch up when it resumes. Event kinds we never registered for are acknowledged and dropped.
- **Processor.** It only claims `order` events (the claim takes a resource type filter, the catalog and inventory processors of T4 and T7 claim their own) and only while the connection is active. A change of an order is serialized across replicas and against the reconciler by a lease named `order-status:<uuid>` (a busy order is retried in 5 s). The shop reads at most 60 orders a minute for events (the rest is deferred 15 s).
- **Guard, exactly.** The payload is trusted only if it has a usable `new_state`, is strictly newer than `last_remote_event_at`, and is more than 5 s away from `last_local_patch_at`. An event more than 5 s older than `last_remote_event_at` is dropped without a read. Anything else (equal or just older, next to our PATCH, no state or an unknown status, events listed by the poller, which carry no state) re-reads the order and applies what HubRise has now. `last_remote_event_at` only moves forward (`GREATEST`) and is set from the event time after the change was applied.
- **Defer window.** An event for an unknown id waits while any `order_create` is queued or sending for an order without a HubRise id, for up to 10 minutes from its arrival (15 s growing to 2 min between looks); after that the order is read and matched through `private_ref`, the HubRise id is adopted (`MarkSent`, the still queued create then only closes its row), or the id is cached as foreign (not a UUID of ours, no such order, or another HubRise order claiming the `private_ref` of a known one).
- **Rules after the mapping.** The remote status is recorded before the local order is touched (a fact about HubRise, and what keeps the outbound side from sending an older status over it). A local terminal status is never moved by a remote one: the order keeps its status and is flagged `STATUS_CONFLICT`. `delivery_failed` flags `DELIVERY_FAILED` only. A remote cancel of an online-paid order flags `REMOTE_CANCELLED_PAID` unless `auto_refund_on_cancel`; with it, a payment that cannot be refunded (`ErrNotRefundable`) flags `REMOTE_CANCEL_FAILED` at once and the event is retried with backoff (30 s doubling to 30 min) until 8 attempts, after which it is `failed`; any other failure of a cancel flags the order only when the attempts run out. `awaiting_collection` on a delivery order changes nothing locally, and the reconciler status diff treats it as in sync.
- **Applying.** The processor and the reconciler (through `RemoteOrderHandler`) apply a change through the `OrderTransitioner` port, implemented in the resolver package on top of `Resolver.ApplyOrderUpdate` with the admin pool and the HubRise origin marker, so the payment settlement, coupon rollback, e-mail, push, live activities and `orderUpdated` topics are those of a dashboard change and nothing is queued back.
- **Poller.** Every 10 minutes (lease `callback-poller`, background class) it lists `GET /callback/events` (10 pages of 100 at most), stores the events it does not have, then acknowledges them; an event it could not store stays listed.

## 8. Inventory and sold-out

- **Provenance rule (review decision).** The system never "restores" availability it did not take away. Each link carries `inventory_sold_out` (true only while the current unavailability was caused by HubRise inventory) and `catalog_disabled`. Hand-set `is_available = false` in production data (or unavailability from any non-HubRise reason) is never flipped back by an inventory sync.
- **Inbound.** On `inventory.update` / `inventory.patch`, or the 30 min poll: `GET /location/inventory`. The payload of an inventory event is never trusted for the stock (the shape of a patch `state_change` is not documented in detail): every event means "read the inventory again", and a batch of events costs one read and one sync. For each entry: `sku_ref` -> product link; `option_ref` -> **all** choice links with that option ref. `stock = 0`: if the row is currently available (or HubRise itself disabled it, `catalog_disabled`), set `is_available = false`, `inventory_sold_out = true`, `sold_out_until = expires_at`; if it is already unavailable for a local reason, record the stock and expiry on the link but do not take ownership (`inventory_sold_out` stays false). Positive stock or entry absent: only rows with `inventory_sold_out = true` are made available again (and the flag cleared); the stock number is stored on the link for display (no per-order stock accounting in v1). Only links under `sync_inventory`; unlinked refs are ignored. Changes publish `productUpdated` (for a choice, the product it belongs to). Expired `stock 0` entries are released by the 1 min sweeper and by the `inventory.patch` expiry notice (which is simply another event that makes the processor read the inventory), again only where `inventory_sold_out = true`. For managed choices, effective availability is `NOT catalog_disabled AND NOT inventory_sold_out`: a released choice that the catalog disables stays unavailable.
- **Atomic provenance.** Taking over and releasing a sold-out state are one transaction (`AvailabilityStore.TakeOver` / `Release`) that flips the link flag with a compare-and-set (`WHERE inventory_sold_out` / `WHERE NOT inventory_sold_out`) and then the availability of the local row. A staff toggle that clears the flag between a sync's read and its write therefore wins: the release finds the flag gone and does nothing. A sync, the sweeper and the baseline also take the `inventory-sync` lease (compare-and-set row in `hubrise_job_leases`), so two replicas never apply the inventory at once; an event that finds it taken is deferred 5 s without counting an attempt, a poll tick just skips. A product whose `inv:sku:<ref>` outbox row is still pending or being sent is skipped by the inbound apply: HubRise has not heard of the shop's change yet, so what it reports is stale.
- **Baseline on first enable.** The first time `sync_inventory` becomes effective (`inventory_baseline_at IS NULL`), local state is authoritative for what the shop already decided: every linked product that is currently `is_available = false` is pushed to HubRise (`stock "0"`, outbound), and `inventory_baseline_at` is stamped. Products that inventory sold out or that the HubRise catalog disables are not pushed (HubRise already knows). Queuing is idempotent, so a failure before the stamp is simply retried. Until the baseline is done, inbound "entry absent" never restores anything. Tests: pre-existing manual unavailability survives enabling sync, the 30 min poll and a full sync.
- **Outbound.** `AvailabilityChanged` (from a dashboard / MCP toggle, never from an inbound apply) clears `inventory_sold_out` on the link (the shop now owns that state) and writes an `inventory` outbox row with dedupe key `inv:sku:<ref>` (latest pending state wins; a `sending` row is never merged into) sent as `PATCH /location/inventory [{sku_ref, stock: "0"}]` or `stock: null` to make it available again. The payload is computed from the product's state at send time. An inbound change applied with the HubRise origin marker does not enqueue an echo.
- **Order validation.** Pricing/quoting already refuses unavailable products (`PRODUCT_UNAVAILABLE`). It additionally refuses a selection of an unavailable choice (`product_choices.is_available`, migration M5) with the **existing** code `SELECTION_INVALID` (no new code, so stored apps behave).
- **Workers.** The outbox worker sends the `inventory` rows (the same drain loop, claim and lease as the order rows; a worker built without the availability store never claims them). `InventoryEvents` claims the `inventory` events; `InventoryJobs` runs the 30 min read (background class) and the 1 min sweeper, each behind its own cadence lease; `CatalogDrift` runs the 6 h check and, every 30 s, collapses the catalog events older than 30 s into one check (one `UPDATE ... RETURNING` count, so two replicas cannot both get them). The check itself is the catalog service's `CheckDrift` (hash comparison, auto-import or "update available", never an automatic mass retire, section 5.5 and A2), reached through the `CatalogDriftChecker` port; a failed check is not repeated for the events it consumed, the 6 h check is the backstop. The inventory PATCH needs the `inventory.write` scope: a 403 is connection level like everywhere else and pauses the pipeline, so the OAuth flow must request it.
- **Conflict.** One truth: the HubRise inventory. A dashboard toggle is pushed to it; if HubRise later reports different, the later event wins (subject to the provenance rule above).

## 9. Security

- **Token at rest.** AES-256-GCM, key `HUBRISE_TOKEN_KEY` (32 bytes, base64), key version byte for rotation. Decrypted only inside the client constructor; never logged, never in GraphQL, never in `staff_audit_log` variables, stripped from errors. `zap` fields use a `Redacted` type.
- **Callback authenticity.** HMAC-SHA256 hex over the raw body with `HUBRISE_CLIENT_SECRET`, `hmac.Equal`, body capped at 1 MB (already the global cap). **Rate limiting only applies to FAILED verifications** (30 per minute per client IP, keyed on `c.ClientIP()` which is the CF-Connecting-IP behind the tunnel); a request with a valid signature is never limited, so HubRise retry bursts (6 retries, event loss after that) cannot be turned into 429s by other traffic sharing a bucket. Test: 20 signed events in a burst all get 200. No signature or bad signature: 401 and nothing stored. Events carry unique ids so replays are harmless.
- **OAuth.** Authorization code flow; `state` is a random nonce stored in `hubrise_oauth_states` bound to the admin user, one use, 10 minutes. The callback endpoint is public (the browser lands on it) but accepts only a valid stored state. The code is exchanged server-side exactly as documented (`docs/hubrise/02-authentication.md`, confirmed by moyun-pos `oauth.rs`): `POST /token`, `Authorization: Basic base64(client_id:client_secret)`, form body `code=...`. The redirect after success goes to `APP_DASHBOARD_URL`.
- **Authorization.** Every GraphQL operation is `@admin`; the existing audit extension records mutations in `staff_audit_log`. The two REST endpoints record custom audit entries (`hubrise.connect`, `hubrise.disconnect`).
- **Least privilege.** Scope `location[orders.write,customer_list.write,catalog.read,catalog.write,inventory.read,inventory.write]` (`customer_list.write` since A1, `catalog.write` since A15, needed only by the PUBLISH direction). `connection.scope` stores the scope that was requested at the last authorization; a connection whose scope lacks `catalog.write` is reported as needing a reconnect before it can publish (A15).
- **SSRF / host pinning.** HubRise base URLs come from env only; the client refuses redirects to other hosts.

## 12. Failure modes

| Situation | Behaviour |
|---|---|
| HubRise down or slow | Orders still created, paid, shown in the dashboard; outbox retries; nothing user-visible breaks |
| 401 (revoked, unpaid, blocked) | `auth_error_at` + `last_error`, workers pause the pipeline without burning attempts, banner in the dashboard status, Sentry; reconnect clears it |
| 429 | client-side limiter plus backoff; catalog and order-list reads throttled to under 10/min |
| Callback lost | event poller + reconciler + 6 h catalog drift check |
| Connection-level refusal (401 or 403) | pipeline pauses, nothing is parked, banner + Sentry; reconnect resumes |
| Orders changed while a push is backing off | create is built with the current status at send time; queued status rows are covered or sent in FIFO order |
| Reconnect to another location/catalog | blocked until old links are cleared (`HUBRISE_RELINK_REQUIRED`) |
| Remote cancel of an online-paid order | no automatic refund unless `auto_refund_on_cancel`; flagged for staff otherwise |
| Stale rows after a long pause | aged out per kind (section 6.1), never replayed |
| Migration cannot get its lock | `lock_timeout` aborts the pre-upgrade hook, the deploy fails before any pod rolls and the old pods keep serving; re-run the deploy (A10) |
| Two replicas | SKIP LOCKED claims, advisory locks on singleton jobs and on the catalog import; the API client Limiter is per process: build it from `DefaultLimits().Split(replicas)` so the replicas together stay under the per connection caps |
| Catalog invalid, empty or suspicious | an empty catalog is rejected; retiring more than 30 % of linked products (min 5) needs `confirmRetire` and is never applied by a scheduled import; partial failure rolls back the batch |
| HubRise order never accepted | after 5 min in `new` the order is flagged for staff (visible in `hubriseStatus.attention`) |

## 13. Production rollout and rollback

1. Deploy code with the new env unset: only the additive migrations run (new tables plus six nullable / defaulted columns, no constraint, each behind a 5 s lock timeout); behaviour identical. This is the first release and can sit there. If a migration cannot get its lock, the pre-upgrade hook fails and the deploy stops before any pod rolled (A10): re-run it.
2. Deploy tsb-dashboard with the HubRise settings page and managed-product UI **before** enabling catalog sync (otherwise a price edit on a managed product returns `HUBRISE_MANAGED` to an unprepared UI). In PUBLISH mode nothing is locked, so the order does not matter for correctness, but the first publish is confirmed from that page.
3. Set `HUBRISE_*` secrets (tsb-infra SOPS), restart. Connect from the dashboard.
4. Enable and adopt, then turn the features on one by one, each step reversible. Every feature toggle starts off (A12), so: connect, `enabled` on (nothing leaves yet), `LINK_ONLY` adoption so that items carry refs, then orders push (only open orders from the moment it is turned on are pushed) -> status sync -> customers -> inventory (the first enable pushes the shop's existing sold-out products to HubRise as the baseline) -> catalog sync (requires a `DRY_RUN` of the current catalog within 24 h; the refund-on-cancel switch stays off until the owner decides).
5. Rollback ladder: switch the catalog direction to NONE (publishing stops, the HubRise catalog keeps what was last published); toggle a feature off; `enabled = false` (everything pauses, locks released); disconnect; unset env (module inert again); goose Down of the migrations (all droppable; the data they hold is HubRise-derived).

- Registered users: just before the `order_create` POST, the worker upserts the customer (`POST /customer_lists/:id/customers` with `private_ref` = user UUID when there is no link, otherwise `PATCH` when the content hash changed) and sends `customer_id` on the order instead of a guest `customer` object. - On a profile update (name, email, phone), enqueue a `customer` outbox row (new outbox kind, so the M3 CHECK is widened in the new migration on the NEW table only, which is allowed).
- On account deletion (the existing user deletion / anonymisation path), enqueue `POST /customer_lists/:id/customers/:id/anonymise`; this must happen even if the local user row is deleted afterwards (payload carries the HubRise customer id).

A10. **Deploy order and schema compatibility (rewritten 2026-10-24; supersedes the first version of A10 and the matching claims of sections 4, 12 and 13).** The migrations now run in a pre-upgrade Helm hook of tsb-infra (a Job that runs the `tsb-migrate` binary of the NEW image, `-cmd=up`), BEFORE `helm upgrade --atomic` rolls the pods. Consequences, all binding for every later migration and query:
- A failed or lock-starved migration (the `lock_timeout` of section 4) fails the hook and therefore the deploy, before any pod changed: the old pods keep serving on the old schema. The first draft's "new binary on the old schema" window no longer exists, so no code path has to tolerate a missing column.
- The remaining window is the reverse: during the rollout the OLD pods (and, after a rollback, the old image) run on the NEW schema. So migrations are additive only (nullable or defaulted columns, new tables, no drop, no rename, no new constraint on a table that already holds data, a working `Down` that is only used on purpose), and production code never depends on the column set of a table.
- **No `SELECT *`.** Every production query lists its columns (`db.Columns(...)` or an explicit list). The guard test in `pkg/db` (`TestNoSelectStar`) fails the build on `SELECT *` and on any `alias.*` column in the SQL text of non-test Go code (and `RETURNING` clauses list their columns too, by the same rule of review); the `Channel *string` / `orders.channel` scan-safety item of M6 is thus covered by construction, not by an audit. New HubRise code (A15 included) must pass that guard from its first commit.
- The old "release 1 = schema only, release 2 = code" split is no longer needed. Rolling back the image is safe as long as the migrations stay additive; only `goose down` is a deliberate act.

As built (T7B, customer list sync):

- **Client and mock.** `pkg/hubrise` has `CreateCustomer`, `UpdateCustomer`, `AnonymiseCustomer` and `FindCustomerByPrivateRef` (customer list endpoints). A PATCH sends only the fields that are set, so a field cannot be cleared through it. The private_ref lookup is charged to the order lookup share of the 10 a minute list bucket. The mock serves one customer list (`hubrisetest.CustomerListID`), hides a customer's private_ref from other clients, refuses a `customer_id` that does not exist or is anonymised, and `DeleteCustomer` plays a customer lost at HubRise.
- **Lazy creation.** A customer is created the first time a registered user's `order_create` is sent, not at registration (the list then only holds people who ordered). `CustomerSync.ForOrder` runs in the worker right before the POST: the profile is read as it is NOW (not from the payload snapshot, so a profile edited meanwhile is not overwritten with older data), the delivery address comes from the order's frozen customer object, and the order gets `customer_id` (never also the guest object).
- **Hash.** `hubrise_customers.content_hash` is `<profile hash>|<address hash>` of what was last written. The profile is PATCHed when its hash changed, the address only when a delivery order brings one that differs from the last written. A pickup order leaves the address HubRise has.
- **Idempotent creation.** The link row is inserted BEFORE the POST (`Begin`), with a NULL customer id. A link that already exists without an id means a creation was attempted and its answer may have been lost, so the customer is looked up by `private_ref` (the user id) before another is created; this also covers a different order of the same user reaching the customer after a failed attempt. A PATCH that meets a 404 forgets the id once, looks the customer up again and creates it if HubRise really lost it. Writes of one customer are serialized across replicas by the lease `customer:<user uuid>` (a busy customer puts the row back for 5 s without counting an attempt).
- **Orders are never held back by the customer list.** A 400/422/404 from the customer list (bad email, unknown list) sends the order with the guest object; a failure that may pass (429, 5xx, timeout) delays the order, up to 3 claims, then the guest object goes out. A 401/403 is connection level and pauses the pipeline like every other call.
- **Profile updates.** The user service has a `ProfileObserver` port (installed with `SetProfileObserver`, nil in standalone). A change of first name, last name, email or phone queues a `customer` row (dedupe key `cust:<user uuid>`, no order id) only when the user already has a HubRise customer; pending rows of one user collapse (the profile is read when the row is sent). A profile row older than 24 h is skipped (the next order carries the profile), a refused one is parked.

Accounts are anonymised rather than deleted, so the link row stays and gets `anonymised_at`; an anonymised link is never written again and later orders of that user use the guest object.

## 21. Dashboard-owned menu (amendment A15, binding)

A15. **Dashboard-owned menu published to HubRise (owner decision 2026-10-24: "only the dashboard edits the menu").** The local database, edited through the dashboard (and the MCP/POS paths that go through the same service), is the single owner of the menu. When the new catalog direction PUBLISH is on, every menu edit ends up in the HubRise catalog so that the EPOS (moyun-pos, which only READS the catalog and takes the product code from SKU `custom_fields.code`) sees it. Standalone mode, and installs that never switch the direction, behave exactly as before. This amendment details the design decisions already taken; it does not reverse them. Sections 5.1, 3.3, 9, 10, 13 and 15 and A10 were corrected above; where this text and an earlier one disagree, this one wins for PUBLISH mode, and IMPORT mode is unchanged.

### A15.1 HubRise facts it relies on (re-read 2026-10-24 at hubrise.com/developers/api/catalog-management)

- `PUT /catalogs/:id` with `data` CLEARS and RECREATES the whole catalog content from the body (`name` is optional; omit it so the catalog is never renamed). There is no per-item endpoint, no ETag, no `If-Match`. The response returns `id`, `name`, `created_at`, `data`. Ids of nested elements may change after a PUT, refs are the stable keys (our link table already keys on refs; only the cached `hubrise_id` columns are refreshed from the response).
- Upload shape of `data`: `variants[{ref,name}]`, `categories[{ref,parent_ref,name,description,tags,image_ids}]`, `products[{ref?,category_ref,name,description,tags,nutrition,tax_rate{delivery,collection,eat_in all three or none},image_ids,skus[]}]`, SKU `{ref?,name? (unique per product, one unnamed allowed),restrictions,price,price_overrides,option_list_refs,tags,barcodes (8/12/13 digits),custom_fields,weight,volume,nb_servings}`, `option_lists[{ref,name,min_selections,max_selections,multiple_selection,tags,options[]}]` with option `{ref?,name,restrictions,price,price_overrides,default,tags,nutrition,weight,volume}`, `deals`, `discounts`, `charges`. A GET returns the same keys but with ids instead of link refs (`parent_id`, `category_id`, `option_list_ids`, `product_id`, `option_list_id`) and the documentation's retrieve example spells `options_lists` and `images_ids` (the typed client already tolerates both; the raw merge must too).
- Option list rules (HubRise validates and auto-corrects): `min_selections` <= `max_selections` (when set) and <= the number of options; `max_selections` > 0 and <= option count unless `multiple_selection`; `multiple_selection` cannot be true when max is 0 or 1; 0 becomes null; values above the option count are capped; no more `default` options than max. Products need >= 1 SKU, lists >= 1 option, a deal >= 1 line with >= 1 SKU that has a ref, `price_overrides` need `price` plus one condition. Refs are unique per kind.
- A location access token can modify a location-level catalog. Modifying an account-level catalog through a location endpoint needs an ACCOUNT token: HubRise answers 401 (403 for a missing scope). The scope `catalog.write` is required for the PUT.
- Images: `POST /catalogs/:id/images?private_ref=...` with `Content-Type` = the image type, raw body, <= 1 MB, JPEG/PNG/WEBP/GIF/BMP; `private_ref` is unique per catalog (reuse), `GET /catalogs/:id/images` lists them (filter by `private_ref`), unattached images are purged after 30 days, there is NO delete endpoint. Reference them by id in `image_ids`.
- `GET /catalogs/:id` stays in the 10 per minute bucket shared with the import and drift jobs. A client never receives a callback for a change it made itself, so every `catalog.update` callback we receive is somebody else's edit.

### A15.2 Catalog direction and the mode switch

- New runtime state on `hubrise_connection`: `publish_catalog BOOLEAN NOT NULL DEFAULT FALSE` and `publish_images BOOLEAN NOT NULL DEFAULT FALSE` (A12 spirit: off by default). The **catalog direction** is derived: `sync_catalog` -> IMPORT, `publish_catalog` -> PUBLISH, neither -> NONE. Both true is impossible: no CHECK is added to the existing table (section 4), so the rule is enforced in Go inside the single `UPDATE ... SET` of `UpdateSettings`/`SetCatalogDirection` which reads the row `FOR UPDATE` in the same transaction, and by a test that hammers both setters concurrently.
- `setHubriseCatalogDirection(direction, acknowledgeLocalOverwrite)` is the only way to change it (`updateHubriseSettings` with `syncCatalog: true` while PUBLISH fails with `HUBRISE_DIRECTION_CONFLICT`; `publishCatalog` is not in the settings input). Transitions:
  - NONE/IMPORT -> PUBLISH: requires connected, not `relink_required`, and `catalog.write` in the stored scope (else `HUBRISE_RECONNECT_REQUIRED`). Atomically sets `sync_catalog = false`, `catalog_auto_import = false`, `publish_catalog = true`, clears `catalog_update_available_at`, resets the publisher row to "awaiting first publish" (`first_publish_confirmed_at = NULL`, dirty). The HUBRISE_MANAGED locks disappear at once (they are keyed on `sync_catalog`). Nothing is written to HubRise until the admin confirms the first publish (A15.7).
  - PUBLISH -> NONE: stops publishing; the HubRise catalog keeps what was last published; links and published-item rows are kept.
  - PUBLISH -> IMPORT: refused while unpublished edits exist (`HUBRISE_PUBLISH_PENDING_CHANGES`) unless `acknowledgeLocalOverwrite`, because the next import would overwrite them; also needs the existing recent `DRY_RUN` (`HUBRISE_PREVIEW_REQUIRED`), exactly as turning `syncCatalog` on does today. Leaving PUBLISH clears the publisher row's dirty flag and external-change warning.
- In PUBLISH mode: `syncHubriseCatalog(FULL)` and `previewHubriseCatalogSync(FULL)` fail with `HUBRISE_PUBLISH_MODE`; `LINK_ONLY` (adoption of existing SKUs so they get their HubRise refs before the first publish) and `DRY_RUN` stay allowed, and `LINK_ONLY` takes the catalog advisory lock (A15.5). `CatalogDrift` does not import and does not set `catalog_update_available_at`; it runs the external-change check (A15.9). `catalogAutoImport` is false and irrelevant. The product guards (`ProductGuard`, `ChoiceGroupGuard`, `ChoiceGuard`) already key on `sync_catalog` and therefore allow everything.
- Inventory sync (`sync_inventory`) is independent and unchanged: availability (`is_available`, option sold-out) never travels in the catalog, it stays on `PATCH /location/inventory` (decision 3). A product the shop makes unavailable is NOT written as `restrictions.enabled = false`; the publisher never writes `enabled = false` except the deal-retention case of A15.4.

### A15.3 Data model (migration `20261024190000_add_catalog_publish.sql`, additive)

All statements on existing tables sit behind `SET LOCAL lock_timeout = '5s'`; no CHECK is added to an existing table that holds data; Down is working.
1. `ALTER TABLE hubrise_connection ADD COLUMN publish_catalog BOOLEAN NOT NULL DEFAULT FALSE, ADD COLUMN publish_images BOOLEAN NOT NULL DEFAULT FALSE`. Down drops them.
2. `hubrise_catalog_publish` (single row, `id BOOLEAN PRIMARY KEY DEFAULT TRUE CHECK (id)`, the migration inserts the row): `change_seq BIGINT NOT NULL DEFAULT 0` (bumped by every menu change), `dirty_since TIMESTAMPTZ`, `last_change_at TIMESTAMPTZ`, `next_attempt_at TIMESTAMPTZ`, `attempts INT NOT NULL DEFAULT 0`, `lease_holder TEXT`, `leased_until TIMESTAMPTZ`, `last_started_at TIMESTAMPTZ`, `last_published_at TIMESTAMPTZ`, `last_published_seq BIGINT NOT NULL DEFAULT 0`, `last_published_local_hash TEXT`, `last_published_remote_hash TEXT`, `first_publish_confirmed_at TIMESTAMPTZ`, `external_change_at TIMESTAMPTZ`, `last_error TEXT`, `last_error_code TEXT`, `last_error_at TIMESTAMPTZ`, `blocked_at TIMESTAMPTZ` (set by a permanent refusal, cleared by the next change or a manual publish), `updated_at`. It is a state machine row, not a queue: the deduplication of "one pending publish" is the row itself. The outbox is deliberately NOT reused (its `kind` CHECK, per-order FIFO and per-row attempts do not fit a singleton whole-catalog job, and widening that CHECK would touch a table that carries live orders).

4. `hubrise_catalog_links.origin` gains the value `published` (new item whose ref the shop generated). The table belongs to this unreleased series and is small; the migration drops the origin CHECK found by `pg_get_constraintdef` in a `DO` block and adds the widened one (`SET LOCAL lock_timeout`). ### A15.4 Building the catalog: refs, mapping and the field-by-field merge

**Pipeline** (all pure functions in `internal/modules/hubrise/application/catalog_publish_*.go`, tested without HTTP): `LocalSnapshot` (already exists: categories, products, groups, choices with texts) + links + connection settings + base HubRise catalog (RAW JSON) -> `Plan` {new links, desired items with hashes, merged `data`, changes, warnings, blockers, removals, foreign}. The merged `data` is what gets PUT.

**Raw JSON, not typed structs.** `pkg/hubrise` gets `GetCatalogRaw` (returns the response `data` as `json.RawMessage`) and `ReplaceCatalog(ctx, id, data json.RawMessage)`. The merge decodes `data` into generic Go values (`map[string]any`, `[]any`, numbers via `json.Number`/`UseNumber` so no float rewriting) so unknown keys at any depth survive. The typed structs are only used for reading the keys the planner needs. Normalization of the base for upload: id references become ref references (`parent_id` -> `parent_ref`, `category_id` -> `category_ref`, `option_list_ids` -> `option_list_refs`), the element ids and `product_id`/`option_list_id` are dropped, `options_lists`/`images_ids` spellings are mapped to `option_lists`/`image_ids`. An element the base has without a ref (a product, an option) is kept positionally; an element that needs a ref for linking and has none (a category or option list, a deal SKU) makes a blocker `BASE_MISSING_REF` in the preview (never guessed).

**Ref assignment (stored before the PUT).**
- A linked item keeps its link's `hubrise_ref` for ever.
- A new category: ref = its slug (unique, immutable, URL safe); on a collision with any base ref, `c-<first 8 hex of the uuid>`.
- A new product: SKU ref = the product `code` when set, matches `[A-Za-z0-9._-]{1,40}` and is unique case-insensitively among all SKU refs in base + links + this run; otherwise `p-<first 8 hex of the uuid>` (12 on collision). The ref never changes afterwards even if the code does (the code travels in `custom_fields.code`). HubRise product ref = the SKU ref, one SKU per product (mirror of the import, section 5.3), SKU unnamed.
- A new choice group: option list ref `g-<8 hex of the group uuid>`; a new choice: option ref `o-<8 hex of the choice uuid>` (unique within its list). Link keys are `skuRef|listRef` and `skuRef|listRef|optionRef` as in section 4.
- New refs are written as link rows (`origin = published`) in one transaction under the catalog advisory lock BEFORE the PUT, so the order push, the inventory sync and a retry after a crash use the same refs. A link whose item is not in `hubrise_published_items` yet is simply unpublished; orders for it still carry the ref (HubRise accepts unknown SKU refs on orders; the debounce keeps the gap to seconds) and nothing fails.

**Field-by-field.** "Owned" = overwritten from the local menu on every publish; everything else of the same element is carried over from the base untouched.

| HubRise element and field | Rule |
|---|---|
| category `name` | owned: local name in `catalog_language` (fallback: first available language) |
| category `description` | JSON convention `{"translations":{"fr":..,"en":..,"nl":..,"zh":..}}`: owned only when the base description is empty or already that JSON (other keys of the JSON are preserved, base languages without a local text are preserved); a plain-text description is never replaced (warning `CATEGORY_DESCRIPTION_KEPT`) |
| category `parent_ref`, `tags`, `image_ids` | carried over; a new category is a root category; images per A15.8 |
| category order | array position: owned categories take the slots owned categories occupied in the base, in local `order`; new ones go after the last owned one; foreign ones keep their slot |
| product `name` (HubRise product) | owned for single-SKU products (local name); multi-SKU products (imported as "Product Sku" locals): local name = product name + " " + SKU name when it still starts with the product name, so the part after the prefix goes to `sku.name` and the product name is kept; a local name that does not start with the product name sets `sku.name` to the whole local name with warning `NAME_SPLIT_AMBIGUOUS` (SKU names are unique per product: a duplicate is a blocker) |
| product `description` | owned for single-SKU products (catalog language); for multi-SKU products it is shared, so it is left alone and the text goes to the SKU `custom_fields.translations` only |
| product `category_ref` | owned: the product's category link ref (if the local category is not linked yet it is created in the same plan) |
| product `tax_rate` | owned for single-SKU products, and for multi-SKU products whose sibling locals all share one VAT category: `food` -> `{delivery:"6",collection:"6",eat_in:"12"}`, `beverage` -> all `"21"`, `zero_rated` -> all `"0"`; `out_of_scope` is not expressible: the key is left as in the base and the SKU custom field carries the truth (the importer reads `custom_fields.vat_category` first, so it round-trips). All three keys are always written together |
| product `tags`, `nutrition`, `image_ids` (images off) | carried over; the visibility tags `hidden` and `web:hidden` are the only tags owned (below) |
| SKU `ref` | the link ref (stable) |
| SKU `price` | owned: local price as `"8.90 EUR"` (the currency of the base prices, `EUR` for an empty catalog). If `variant_ref` is set and the SKU has an unconditional price override for that variant (the rule the importer resolves), the local price is written into that rule instead and the base price is left, so the import mapping round-trips; all other `price_overrides` are carried over |
| SKU `restrictions` | carried over untouched (time windows, `variant_refs`, `enabled`). Exception: a SKU still referenced by a preserved deal whose product was deleted locally is kept with `enabled = false` and reported as `RETAINED_BY_DEAL` |
| SKU `tags` | owned: `web:hidden` present iff the product is hidden (`is_visible = false`), which is how the importer reads "hidden" so a later import round-trips; the legacy `hidden` tag is removed when the product is visible; a product-level `hidden`/`web:hidden` tag is pushed down onto every SKU of that product the first time and removed from the product tag list; all other tags carried over |
| SKU `custom_fields` | merged as a map: `code` owned (set when the local code is non-empty, removed when empty: the shop is the truth), `vat_category` owned, `translations.<lang>.name/description` owned for every language the product has a local text in (languages only HubRise has are kept; unknown keys inside an entry are kept), every other custom field carried over |
| SKU `barcodes`, `weight`, `volume`, `nb_servings`, `price_overrides` (other rules), `option_list_refs` of foreign lists | carried over |
| SKU `option_list_refs` | owned for the lists of local groups (one list per (SKU, group), mirror of section 4); refs to lists the shop does not own (foreign lists on a linked SKU) are kept after the owned ones |
| option list `name` | owned (catalog language) |
| option list `min_selections` / `max_selections` / `multiple_selection` | owned: min and max from the local group; `multiple_selection = (max > 1 and the group allows repeated picks)` is not stored locally, so it is derived: kept from the base when the base value is consistent with the new max, else `max > 1`; max is capped by HubRise to the option count unless multiple (so we write `null` for "all options" like the importer reads it); validated against the rules of A15.1 before the PUT |
| option list `tags`, `type` | carried over |
| option `name` | owned |
| option `price` | owned: `price_modifier` as Money; option `price_overrides`, `restrictions`, `default`, `tags`, `nutrition`, `weight`, `volume` carried over |
| option order | local `sort_order`, using the slot rule of categories among owned options |
| `variants`, `deals`, `discounts`, `charges` | carried over verbatim (deal `category_id` normalized to `category_ref`); a deal line naming a SKU that is being removed makes that SKU retained (`RETAINED_BY_DEAL`) instead of breaking the deal |
| any unknown top-level or nested key | carried over |
| deleted locally (a link or a published item whose local row is gone) | removed from the payload: a product removes its SKU (and its HubRise product when that was its last SKU), a group removes its option list unless another SKU still uses that list, a choice removes its option |

**Shared option lists.** HubRise lists may be shared by several SKUs; locally each SKU has its own group (mirror of the import). The planner groups the desired content of all linked (SKU, group) pairs by `listRef`. When every pair of a list is identical (name, min, max, ordered options with refs, names, prices) one list stays shared. When they diverged (the owner edited the group of one SKU), the largest identical subset keeps `listRef` and each other subset gets a NEW list `listRef~<skuRef>` (deterministic, collision-checked), its options keep their `optionRef`, and the group and choice link rows are re-keyed (`skuRef|newListRef...`, `hubrise_ref` updated) in the pre-PUT transaction. The preview lists the split as `UPDATE` with field `listSplit`.

**Hidden and deleted.** A hidden product stays in the catalog with the tag above (never `restrictions.enabled=false`, which the importer reads as `catalog_disabled` and unavailability, a different thing). A product that does not exist locally any more (no delete mutation exists today, but SQL or a future mutation can) is removed.

**Foreign items.** A base element with no link, no published-item row and no local counterpart (a product only the EPOS menu editor created) is *foreign*: carried over untouched by default, listed in the preview (`foreignItems`), and removed only when the admin passes `removeForeign`. The removal set is therefore `published - desired` (+ foreign when `removeForeign`).

**Hashes.** `ItemHash` per owned item is a hash of its owned fields (not of refs or base values); `LocalMenuHash` is the hash of all of them in canonical order; `RemoteCatalogHash` is the hash of the HubRise `data` canonicalized (keys sorted, every `id`/`*_id`/`*_ids` key dropped because ids may change after a PUT). They back the safety net and the external-change check.

**Pre-flight validation (blockers).** Before any PUT the planner checks the payload against the HubRise rules of A15.1 plus ours (unique refs per kind including foreign ones, `category_ref` exists, option list min/max/default rules, every product has a SKU, tax_rate all-or-none, SKU names unique per product, no empty option list, Money format, barcodes). A violated rule is a blocker listed in the preview; `publishHubriseCatalog` refuses with `HUBRISE_PUBLISH_BLOCKED` and the background publisher records `INVALID_MENU` instead of sending something HubRise would 422. The empty local menu (no product) is refused with `HUBRISE_EMPTY_MENU` (a wipe of the EPOS menu by a bug is the worst case).

### A15.5 Change detection and the debounced, durable, two-replica publisher

**Hook (fast path).** The product module cannot import the hubrise module (`coupling_test.go`). The product application service gets an optional consumer-defined port `MenuObserver { MenuChanged(ctx, kind MenuChange, id uuid.UUID) }` (nil in standalone), installed with `SetMenuObserver` by `hubrisewire.Install` exactly as the status observer is installed on the order service, and called after the repository write succeeds (best effort: failure logged, never returned) in `CreateProduct`, `UpdateProduct`, `Create/Update/DeleteChoiceGroup`, `Create/Update/DeleteChoice`. It sits in the service, not in the resolvers, so the MCP tools and any other caller are covered. The image upload that follows `UpdateProduct` in the resolver calls the resolver hook `Resolver.MenuChanged(ctx, MenuImage, id)` after a successful upload. `Resolver.Hubrise` (the `HubriseHooks` of section 3.2) gets `MenuChanged` for that last call; the importer's own repository writes do not notify (import mode). The implementation does one primary-key read of the connection (like the other hooks): when `publish_catalog` is off it returns; otherwise `MarkDirty` runs one statement:
`UPDATE hubrise_catalog_publish SET change_seq = change_seq + 1, last_change_at = now(), dirty_since = COALESCE(dirty_since, now()), blocked_at = NULL, next_attempt_at = GREATEST(LEAST(now() + 10 s, COALESCE(dirty_since, now()) + 120 s), COALESCE(last_started_at, '-infinity') + 30 s)` (`dirty_since` read before the update).
So the publisher waits 10 s after the last change, never starves longer than 2 minutes of continuous edits, and runs at most once per 30 s. Marking happens even while the pipeline is paused (disabled, auth error, relink): the edits are published after the resume.

**Safety net (no hook can be trusted alone).** Categories have no mutation at all today and SQL edits, restores and future writers bypass services. Every 5 minutes a lease-guarded tick (`catalog-publish-scan`, background class, no HubRise call) reads the local snapshot, computes `LocalMenuHash` and compares it with `last_published_local_hash`; a difference with no dirty flag calls `MarkDirty("scan")`. A test writes with raw SQL and asserts the publish follows within one scan.

**Worker.** `CatalogPublisher.Run` ticks every 5 s on every replica. `Claim` is one compare-and-set statement on the singleton row: `UPDATE hubrise_catalog_publish SET lease_holder = $h, leased_until = now() + 90 s, last_started_at = now() WHERE dirty_since IS NOT NULL AND blocked_at IS NULL AND next_attempt_at <= now() AND (leased_until IS NULL OR leased_until < now()) AND first_publish_confirmed_at IS NOT NULL AND EXISTS (SELECT 1 FROM hubrise_connection c WHERE c.publish_catalog AND c.enabled AND c.access_token_enc IS NOT NULL AND c.auth_error_at IS NULL AND c.relink_required_at IS NULL) RETURNING change_seq`. The lease is renewed before the GET and before the PUT (`Extend` fails if lost; then the run stops and writes nothing). The connection is re-read inside the claim like the outbox does, so a disable takes effect on the next claim on every replica. A run:
1. Snapshot: local menu and links read in one `REPEATABLE READ, READ ONLY` transaction (consistent view), `seq` = the `change_seq` taken at claim.
2. `GetCatalogRaw` (catalog bucket, background class; a `*RateLimitError` reschedules at the Retry-After without counting an attempt).
3. Plan (pure). Blockers -> `INVALID_MENU`. Removal threshold or first publish unconfirmed -> the run stops with `last_error_code` and waits for the dashboard confirmation (it never removes silently): `removed >= 5 and removed > 30 % of the published SKUs` (`domain.TripsMassRetire`, same constants as the import) is the threshold; the background publisher never carries a confirmation, only `publishHubriseCatalog(confirmRemovals)` does.
4. New refs and re-keys committed (`pg_advisory_xact_lock` on the same key the import's `InBatch` uses, so a concurrent `LINK_ONLY`/`forgetLinks` and a publish serialize).
5. `ReplaceCatalog` (PUT) with the merged `data`. A plan with zero changes against the base skips the PUT (idempotent; this also resolves the "PUT succeeded, response lost" case on the next run).
6. Success, in one transaction: `hubrise_published_items` replaced by the plan's owned items, `hubrise_id` columns refreshed from the response, `last_published_at/local_hash/remote_hash` stored (`remote_hash` = hash of the response `data`), `external_change_at = NULL`, `attempts = 0`, error fields cleared, `catalog_hash` NOT touched (it is the import hash), and the dirty flag cleared only `WHERE change_seq = $seq`; if edits arrived meanwhile the row stays dirty with `next_attempt_at = now() + 30 s`. The lease is released. `productUpdated` is published for products whose state changed from PENDING (dashboards refresh the publish badge).
7. `last_started_at` makes the 30 s minimum interval hold across replicas and restarts; a crash mid-run only leaves a lease that expires after 90 s.

**Concurrency with other jobs.** The publisher and `GET /catalogs/:id` consumers share the 10 per minute bucket through the existing limiter (publisher = background class, preview/publish buttons = interactive share), so a publish can never starve order lookups. `Limiter.Split(replicas)` applies as before. Inventory and order pushes are untouched by a publish: their refs are stable.

### A15.6 Errors, classification, and what never happens

| Outcome | Behaviour |
|---|---|
| GET 401/403 | connection level, the existing path: `auth_error_at`, whole pipeline paused (including publishing), banner |
| PUT 403, or 401/403 with a stored scope that lacks `catalog.write` | NOT connection level: no global pause (orders, status and inventory keep flowing). `last_error_code = WRITE_SCOPE_MISSING`, `needsReconnectForWrite` true, publisher blocked until reconnect (reconnect clears it) |
| PUT 401 (or 403) with the scope present | probe `GET /location` (not in the 10/min bucket): a 401 there too means a revoked token -> global auth error; otherwise the catalog is account level: `ACCOUNT_CATALOG`, blocked, message "this catalog belongs to the HubRise account; connect with an account token or use a location catalog". The account-level case is also detected BEFORE the PUT when the GET shows no `location_id` (then the first publish is refused with `HUBRISE_ACCOUNT_CATALOG` without trying) |
| GET/PUT 404 | `CATALOG_NOT_FOUND`, blocked until reconnect or relink |
| 422 | permanent for this content: `REJECTED`, `last_error` = first 5 `field: message` pairs (truncated to 500 chars, no tokens), `blocked_at` set; the next menu change, or `publishHubriseCatalog`, re-arms. Never retried in a loop; Sentry event with the field names only |
| 429 | the client limiter parks the connection until Retry-After; the run is rescheduled there without burning an attempt |
| 5xx, timeout, connection error | `UNAVAILABLE`, `attempts++`, `next_attempt_at` backoff 30 s doubling to 15 min, the dirty flag stays: nothing is ever dropped or parked |
| any other panic or storage error | the worker supervisor restarts it; the lease expires |
Never: the publisher never deletes a local row, never imports, never calls HubRise while `enabled` is false, auth-errored or relink-required, never sends a token or a payload to a log (logs carry counts, refs of at most 20 changes, durations). The PUT body can hold prices and names only (no customer data).

### A15.7 Safety guards

- **First publish needs a dry-run preview and an explicit confirmation.** After switching to PUBLISH, `first_publish_confirmed_at` is NULL and the publisher never writes. The dashboard calls `previewHubriseCatalogPublish` (one GET + the pure plan, writes nothing, returns `planHash`, counts, every change, foreign items, warnings, blockers) and the admin confirms with `publishHubriseCatalog(confirmRemovals, removeForeign, planHash)`; the server recomputes the plan, refuses with `HUBRISE_PREVIEW_STALE` when `planHash` differs (a menu edit or an external HubRise edit changed the added/updated/removed/foreign key sets since), and only then writes and stamps `first_publish_confirmed_at`. `planHash` = sha256 over the sorted lines `A:<entity>:<key>`, `U:...`, `R:...`, `F:...` of the plan, so cosmetic field changes do not stale it but a different removal set does.
- **Mass removal.** Any publish (first or not) whose removal set trips `TripsMassRetire(removed, published SKUs)` needs `confirmRemovals` plus the `planHash`; the background publisher never has it and stops with `last_error_code = REMOVALS_NEED_CONFIRM` shown as a banner with the preview button. `removeForeign` counts toward the removal set.
- **Pauses.** `enabled = false`, an auth error, a relink requirement and disconnect all stop the publisher (claim predicate) while edits keep marking dirty. A reconnect to another location/catalog (`relink_required`) additionally resets `first_publish_confirmed_at` to NULL, so the new catalog gets a fresh preview and confirmation, and clears `hubrise_published_items`.
- **Empty menu** and **blockers** are refused (A15.4). **Account-level catalog** is refused before writing (A15.6).
- **Audit.** The three mutations are `@admin` and recorded by the existing staff audit extension; the background publish writes a `staff_audit_log`-style entry `hubrise.catalog.publish` (counts only) through the audit adapter.

### A15.8 Images (phase 2, behind `publish_images`, default off)

When off, `image_ids` of categories, products and deals are carried over from the base untouched (so a publish never loses images added at HubRise). When on: for each visible local product with an image (object keyed by the product UUID in the product bucket) the publisher builds a derivative of at most 1 MB (JPEG/PNG/WEBP/GIF/BMP kept as is when small enough; otherwise decoded and re-encoded as JPEG with decreasing quality and a 1200 px long side), and computes its MD5. It lists the catalog images once per run (`GET /catalogs/:id/images`) and reuses an image whose `private_ref` is `tsb-product-<uuid>-<md5 first 12>`; otherwise `POST /catalogs/:id/images?private_ref=...` uploads it (3,000/min images limit, uploads before the PUT, at most 50 per run, the rest on the next run). The returned id goes into the product's `image_ids` (replacing the product's previous owned id, keeping foreign ids). A product image removed locally empties the owned id. Images that become unattached are purged by HubRise after 30 days (no delete endpoint, nothing to do). A failed upload is non-fatal: the product keeps its previous `image_ids` and the run reports a warning `IMAGE_FAILED`. Image changes mark the catalog dirty through the resolver hook (A15.5). Settings input `publishImages` is refused with `HUBRISE_RECONNECT_REQUIRED` when the scope lacks `catalog.write`.

### A15.9 Callbacks, drift and external change in PUBLISH mode

- A `catalog` event (`create/update/delete`) in PUBLISH mode never reaches the importer. `CatalogDrift.CheckEvents` instead sets `external_change_at = event time` (collapsing a burst), and `catalog.delete` sets `last_error_code = CATALOG_NOT_FOUND`. Our own PUT never produces such an event (HubRise does not call back the author), so it is always somebody else's edit.
- The 6 h `CheckScheduled` tick, in PUBLISH mode, fetches the catalog (one catalog-bucket GET) and compares `RemoteCatalogHash` with `last_published_remote_hash`; a difference sets `external_change_at` too (covers a lost callback). It does not mark the catalog dirty.
- The warning is shown in the dashboard ("HubRise was edited elsewhere; the next publish keeps unknown fields and overwrites the fields the dashboard owns"). It is cleared by a successful publish, or by `acknowledgeHubriseExternalChange`. The preview already shows what would be overwritten, because modeled fields that differ from the base appear as `UPDATE` entries.
